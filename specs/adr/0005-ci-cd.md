# ADR-0005 — CI/CD com GitHub Actions; implantação pelo Coolify

**Estado:** Aceita · **Data:** 12/10/2026

## Contexto

Arthur pediu uma esteira que **verifique os tipos, construa os contêineres e rode os testes**. A implantação é no Coolify (VPS), com Dockerfiles próprios. O repositório fica no **GitHub** (confirmado por Arthur).

## Decisão

Decidido por Arthur (12/10/2026): **o CI só verifica e constrói. Não publica imagens nem aciona implantação** (sem webhooks).

| Gatilho | Tarefas, nesta ordem (a falha de uma interrompe a esteira) |
|---|---|
| Pull request e push em qualquer branch | 1. Instalar dependências (pnpm, com cache) → 2. **Verificar tipos** (`tsc --noEmit` em todos os pacotes; `astro check` na landing) → 3. **Lint** (ESLint e `prettier --check`) → 4. **Testes** de integração da API, com PostgreSQL como contêiner de serviço do Actions → 5. **Build da imagem Docker de cada aplicação** (`landing`, `crm-web`, `crm-api`), sem publicar |

- Os passos podem rodar em jobs paralelos por aplicação, desde que cada aplicação passe por tipos, lint, testes (quando houver) e build.
- A `main` fica protegida: merge só por pull request, com o CI aprovado.

## Implantação

Fora do CI. O Coolify constrói e implanta cada aplicação a partir do próprio repositório no GitHub, usando os mesmos Dockerfiles que o CI valida **[H]**.

**Risco:** o Coolify não espera o resultado do CI. **Mitigação:** a proteção da `main` garante que só chega lá código que passou pelo CI, então o Coolify sempre constrói um commit já verificado. Push direto na `main` fica bloqueado.

## Consequências

- Nenhuma alteração chega à `main`, e portanto à produção, sem passar por tipos, lint, testes e build.
- Não há segredos de implantação no GitHub.
- A imagem de produção é construída de novo pelo Coolify, a partir do mesmo Dockerfile e do mesmo commit que o CI construiu. Se um dia for necessário garantir que é a mesma imagem byte a byte, a evolução natural é publicar no GHCR (alternativa descartada por enquanto).
